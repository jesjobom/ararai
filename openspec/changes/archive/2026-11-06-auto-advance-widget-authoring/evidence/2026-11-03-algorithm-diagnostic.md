# Algorithm-stage failure on SM-S901E

The retained device was running ArarAI debug versionCode `29894558` (versionName `202611022138`) when JJ reported repeated failures creating a new ranked web-results widget. Its checked-in model catalog declares `widget_authoring_pipeline_v1` for the selected Gemma 4 E4B; the model was eligible. Device time zone was America/Toronto (EST).

An app-private, read-only copy of the widget database was queried for session and attempt metadata only. Raw user instructions and model artifacts were not filed. The active session had accepted feasibility and was `AwaitingRetry` at `algorithm`. Algorithm attempts 1, 3, 4, and 6 failed with `InvalidAlgorithm` after capturing 425–447 byte artifacts. Attempts 2, 5, and 7 were interrupted with `RuntimeUnavailable`. The captured structural metadata showed that the first candidate kept `collection_list` but added a dependent formatting transform; later candidates kept a transform and switched to one-item `collection_card`, contrary to the requested ranked list. The application correctly rejected those candidates rather than silently reducing the result count.

The platform log independently records Android `lmkd` reclaiming `com.jesjobom.ararai` during a later generation at 22:21:38 EST because of low swap and 302% thrashing. The preceding model load/generation events were present. This is a process-memory interruption, separate from the captured `InvalidAlgorithm` failures; neither is evidence of a missing model capability or a generation watchdog timeout.

The corrective code strengthens the list-specific algorithm context, capture schema guidance, and `InvalidAlgorithm` repair instruction: unmodified ranked results use `collection_list`, one `web_search_top_results` call, and no post-call formatting transform. Validation remains strict; no model artifact is automatically rewritten or accepted. The memory-pressure failure is not claimed fixed by this guidance change.

`scripts/quality-gate.sh` passed after the corrective change, including Android unit tests, lint, debug/release-candidate builds, R8 verification, and strict OpenSpec validation (11 items passed, none failed). The revised debug APK SHA-256 is `0cdbeeaf8bfe923a9393ad63672a4338de6cafdb02835746c97e709160fab505`, versionCode `29894613`, versionName `202611022233`. `adb install -r` returned `Success`. The package update time advanced from `2026-11-02 21:43:11` to `2026-11-02 22:37:38` device time, while firstInstallTime remained `2026-10-04 22:04:26`. The in-progress session remained `AwaitingRetry` at `algorithm` with its feasibility checkpoint accepted. No uninstall, storage clear, connected instrumentation run, or authoring retry was performed.

JJ started algorithm attempt 8 on the revised APK. It completed in about 33 seconds and produced an accepted `collection_list` algorithm with exactly one `web_search_top_results` tool call and no transform. The application automatically accepted that checkpoint and started `call:step_1`. This confirms the revised guidance worked for this physical attempt and that automatic stage advancement occurred. The call-function generation then reached the 90-second stage watchdog, ending `TimedOut`; it captured no artifact. The runtime reported thermal status 2 by cleanup, but the trace does not establish thermal pressure as the sole cause. The session remains `AwaitingRetry` at `call:step_1` with feasibility and algorithm checkpoints intact. This is a new stage failure, not a recurrence of `InvalidAlgorithm`, and no automatic retry was started.
